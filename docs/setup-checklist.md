# CommunityHub Setup Checklist

Start with development essentials. Payment and store accounts can be activated later.

## Development tools

- [ ] Install Node.js LTS and Git
- [ ] Install VS Code or use your preferred Codex environment
- [ ] Create an Expo account
- [ ] Create a GitHub repository for CommunityHub

## Backend and storage

- [ ] Create a Supabase project
- [x] Configure database migrations in `supabase/migrations`
- [x] Define storage buckets and Row Level Security policies
- [ ] Configure separate development, staging, and production environment variables
- [ ] Configure backups/PITR and complete a restore drill before production

## Authentication

- [ ] Configure email verification and password recovery in Supabase Auth
- [ ] Configure recovery deep links: use `https://communityhub-lyart.vercel.app/reset-password` as the Supabase Auth redirect URL. The installed app claims this path with iOS Universal Links and Android App Links; without the app, the same URL remains the web reset fallback.
- [ ] Set the production domain in `apps/mobile/app.json` and `apps/mobile/eas.json` to the final HTTPS domain if it differs from `communityhub-lyart.vercel.app`.
- [ ] Replace `REPLACE_WITH_APPLE_TEAM_ID` in `apps/web/public/.well-known/apple-app-site-association` with the Apple Developer Team ID, then verify the file is available at `https://<domain>/.well-known/apple-app-site-association` with no redirect.
- [ ] Replace `REPLACE_WITH_EAS_ANDROID_SHA256_CERT_FINGERPRINT` in `apps/web/public/.well-known/assetlinks.json` with the SHA-256 signing fingerprint for the EAS production Android build, then verify `https://<domain>/.well-known/assetlinks.json` returns JSON with no redirect.
- [ ] Add the final HTTPS domain to Apple Associated Domains and Android App Links verification before store submission; test both an installed-app link and the browser fallback.

### Recovery-link domain and DNS

The configured staging/preview host is `communityhub-lyart.vercel.app`. For a
custom production host, first add the domain to the Vercel project, create the
DNS record Vercel requests (normally a `CNAME` to the Vercel target, or the
provider's apex record), and use that exact HTTPS host in `app.json`, `eas.json`,
Supabase Auth URL Configuration, and both `.well-known` files. Do not use a
localhost, preview-only, or HTTP URL in store builds. The recovery page at
`/reset-password` is intentionally kept on the web host so the same link works
when the app is not installed.

Verify with:

- `https://<domain>/.well-known/apple-app-site-association` returning JSON with
  `Content-Type: application/json` and no redirect.
- `https://<domain>/.well-known/assetlinks.json` returning JSON with no redirect.
- A Supabase recovery email redirecting to `https://<domain>/reset-password`.
- An installed build opening the native reset screen, and an uninstalled-device
  browser opening the web reset page.
- [ ] For application notifications only, configure the server-only outbox provider URLs and run `pnpm process:outbox` from a protected worker or cron; Supabase Auth confirmation, recovery, and OTP delivery remain managed by Supabase Auth.
- [ ] Choose an SMS OTP provider, such as Twilio
- [ ] Add provider credentials to secure server-side configuration
- [ ] Test OTP delivery, expiry, resend cooldowns, and provider rate limiting

## CI integration secrets

The integration job uses a fresh local Supabase instance on every run; it does not use a shared project. Add these optional GitHub Actions repository secrets only when provider-backed payment integration tests are introduced:

- `STRIPE_TEST_SECRET_KEY` — Stripe sandbox secret key.
- `RAZORPAY_TEST_KEY_SECRET` — Razorpay test secret.

When neither secret is present, CI prints an explicit skip reason for provider payment tests. Never add live credentials, webhook secrets, `SUPABASE_SERVICE_ROLE_KEY`, or client-exposed keys to the repository secrets for this job. The local Supabase URL, anon key, and service-role key are generated by `supabase start` and discarded after the job.

## References

- Copy variable names from `.env.example`; never commit real secrets.
- Follow `docs/environments.md` for environment separation.
- Follow `docs/release-checklist.md` before any store submission.
- Use `pnpm db:reset`, `pnpm db:seed`, and `pnpm test` for local development.
- Run `pnpm reconcile:stock` manually or from a protected cron after deploying stock reservations; it requires `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.
- The weekly retention dry-run workflow requires protected repository secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; it never applies a purge. Keep the service-role secret unavailable to build and client jobs.

## Web E2E tests

The browser suite uses disposable seeded Supabase users only. It never needs
production credentials. Start a local Supabase project and web server, then
export `E2E_BASE_URL`, `E2E_USER_EMAIL`, `E2E_USER_PASSWORD`,
`E2E_ADMIN_EMAIL`, and `E2E_ADMIN_PASSWORD` before running `pnpm e2e:web`.

For a local run, use `pnpm db:start`, `pnpm db:reset`, export the URL, anon
key, and service-role key printed by `supabase status -o env`, then run
`node scripts/seed-e2e-users.mjs`. Export the six `E2E_*` values printed by
that script, start the web app with `pnpm dev:web`, and run `pnpm e2e:web`.
The service-role key is used only by the local seed process and is never passed
to Playwright or the browser.

Install Chromium once with `pnpm exec playwright install chromium`. For the
missing-environment coverage, start a second web process without the public
Supabase variables and set `E2E_MISSING_ENV_URL` to its URL; the test expects
the neutral `Unavailable` page and no development banner.
